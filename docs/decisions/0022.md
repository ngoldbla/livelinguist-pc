# 0022 - Link sherpa-onnx as a shared library on Linux

- Status: accepted
- Date: 2026-11-24
- Decision IDs: D-059
- Related: 0001 (sherpa-onnx), 0002 (llama.cpp), 0005 (Rust), tasks T17, T35

## Context

`sherpa-onnx-sys` 2.0.1 links its prebuilt static libraries by default, which
includes a static onnxruntime. llama.cpp (`llama-cpp-sys-2`, built from
vendored sources) uses `std::regex` in its core (`unicode.cpp`, vocab,
grammar), and so does onnxruntime. With GCC, both carry their own copy of the
same `std::regex` template code, built differently. The linker keeps one copy,
and onnxruntime then runs llama.cpp's.

Running T35 on Linux (2026-11-24): a release `ll-eval` built with
`--features sherpa,llama` aborts as soon as the ASR recognizer is created:

```
munmap_chunk(): invalid pointer
  std::__detail::_Compiler<std::regex_traits<char>>::_Compiler
  onnxruntime::ParseSemVerVersion
  ... onnxruntime::Environment::Create / OrtApis::CreateEnv
  sherpa_onnx::OnlineRecognizerImpl::Create
```

The same binary with only `sherpa`, or only `llama`, runs. An earlier fix
(T17, `docs/qa/2026-11-23-llm-cpu.md`) removed llama.cpp's `common` library,
which stopped a startup abort in debug test binaries, but the core library
still has the clash. Windows (MSVC, static `/MT` everywhere) is not affected:
the owner retest on 2026-11-24 ran both models in one process.

## Options

1. **Shared sherpa-onnx on Linux (chosen).** `sherpa-onnx` with the `shared`
   feature on `target_os = "linux"` only; `static` everywhere else. onnxruntime
   then resolves its own `std::regex` code inside `libonnxruntime.so`. The
   crate's build script copies `libsherpa-onnx-c-api.so` and
   `libonnxruntime.so` next to the build outputs; `.cargo/config.toml` adds
   `-Wl,-rpath,$ORIGIN` for Linux targets because a dependency's link args do
   not reach the final binary.
2. Keep static and run ASR and the simplifier in separate processes on Linux.
   It changes the architecture to work around a dev-platform link problem.
3. Build llama.cpp with a different C++ standard library or hidden template
   visibility. These are fragile flags inside a vendored CMake build we don't own.

## Decision

Option 1. The Windows build is unchanged: same crate, same `static` feature,
same `Cargo.lock`.

## Consequences

- Linux binaries built with `sherpa` need the two `.so` files beside them
  (cargo puts them in `target/<profile>/` and `deps/`). A Linux bridge `.node`
  built with `sherpa` loads them from its own directory as well; Linux is a dev
  platform only (0015), so this is not shipped.
- The Linux build downloads `sherpa-onnx-v2.0.1-linux-x64-shared-lib.tar.bz2`
  instead of the static archive.
- Evidence: after the change, `scripts/privacy-check.sh` prints
  `privacy: PASS` (no `connect()` calls) and
  `cargo test -p ll-eval --features sherpa,llama` passes.

## What would overturn it

A sherpa-onnx release whose static Linux libraries hide their C++ symbols, or
a Linux release target (not planned for 1.0).
