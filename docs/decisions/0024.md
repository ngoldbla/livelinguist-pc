# 0024 - Caption-latency benchmark and CPU-first autoresearch loop

- Status: accepted
- Date: 2026-11-24
- Decision IDs: D-061
- Related: 0001 (ASR runtime), 0006 (latency budgets), 0012 (event envelope),
  0018 (CPU-first v1), 0019 (ASR model), 0021 (packaging)
- Evidence: `docs/qa/2026-11-24-caption-latency-baseline.md`

## Context

The existing Tier 1 metric is not an end-to-end product measurement. It mixes
an audio-clock estimate (`segment.audio_start - 1.1`) with the first Rust-side
partial timestamp, and only the first finalized segment receives a partial
stamp. It never observes the media clock, JavaScript delivery, React commit, or
a presented frame.

The shipped Windows RC is CPU-only. The owner sees slower live captions on a
desktop RTX 5060 Ti testbed than the Apple-silicon implementation shows on
lighter mobile hardware. We need a repeatable number before changing models or
adding GPU inference.

## Options

1. **External media-clock + Windows UIA benchmark (chosen).** Play a pinned,
   captioned, openly licensed local video through the default render endpoint;
   run the real app; poll its accessibility text tree; align observed captions
   to reference cue start times. Persist timings and scores only.
2. Add native capture/present timestamps to cpal, the bridge, and GPUIX. This is
   the strongest eventual instrument, but GPUIX 0.11 exposes no documented
   present callback and the work would delay the first baseline.
3. Time only Rust ASR calls. Cheap, but it misses buffering, endpointing, event
   delivery, UI presentation, and the overlay's final-only behavior.

## Decision

Option 1 for the baseline and parameter search; option 2 remains a follow-up if
UIA quantization or accessibility timing proves too coarse.

- Primary objective: minimize **p95 reference-cue-start → visible partial** in
  the overlay. The overlay is the product's compact live-caption surface.
- Secondary objective: minimize **p95 reference-cue-start → visible final**.
- Quality constraints: at least 80% cue coverage and at least 0.85 mean token
  similarity for the optimized tier. No transcript text is persisted.
- CPU first. GPU ASR is a separate post-baseline track and must not be mixed
  into CPU comparisons.
- Keep shipping defaults unchanged until a candidate wins a screening run and
  a repeated confirmation run. Runtime knobs are explicit `LL_ASR_*` env
  overrides; strict mode never silently falls back.
- The overlay shows the existing verbatim partial above the latest final. It
  does not start simplification or change the two-tier contract.

## Consequences

- The benchmark needs an interactive Windows desktop, Microsoft Edge, audible
  default output, and the real models. It is not a CI unit test.
- UIA observation is a proxy for visibility, with measured polling quantization
  (tens of milliseconds), not a hardware present timestamp.
- Public fixture audio/video and captions stay under gitignored `target/`.
  Fixture URLs, licenses, and SHA-256 values are committed.
- Smaller ASR input chunks and endpoint thresholds become experiment variables.
  The 560 ms model package remains pinned; input chunking is not a model swap.
- A lower number is rejected if cue coverage or similarity regresses, or if it
  increases overruns/finalized-segment loss.

## Addendum 2026-11-25 — first confirmed CPU candidate

The installed RC baseline (3 × 60 s) measured live partial p95 3657 ms and
overlay final-only p95 12658 ms. The overlay partial + 80 ms input chunk + 2
threads candidate (3 × 90 s) measured partial p95 2278 ms with 93.8% cue
coverage and 0.996 mean token similarity. That is a 37.7% partial-p95
improvement versus the RC live view and 82.0% versus the RC overlay's final
p95. The finalized tail remains about 12.5 s; presenting the partial is the
largest UX improvement.

The aggressive endpoint candidate improved p50 but regressed partial p95 and
was rejected. Shipping ASR defaults remain unchanged pending a second
voice/style, WER/CER, tier C, and click-during-live continuity checks.

## Addendum 2026-11-25 — second voice selects 560 ms; click path fixed

The second voice (NASA Elena Serova, public domain) changed the ranking. At
80 ms the partial p95 was 6436–11102 ms in three trials (median 9544 ms) against
5671 ms at 1100 ms; 160 ms showed the same 11.1 s tail. The 560 ms input chunk —
the model's own window — measured 4380–6811 ms (median 4418 ms) with 94.7%
coverage and a stable 2685 ms on the lecture. Four of five measured locales have
identical WER at 560 and 1100 ms (en-US moves 0.149 → 0.1519), the ASR chunk p95
halves (457 → 229 ms), and tier C passes at RTF 0.241, p95 144 ms, 777 MB.

**Shipping default: 1100 → 560 ms, 2 threads, endpoints unchanged.** The 80 ms
candidate stays opt-in. The shipped path (no env overrides) measures 2661–2704 ms
on the lecture (93.8% coverage) and 4380–6811 ms on the second voice (94.7–100%).

The click gate found a pre-existing defect: a click froze captions for the whole
backend run because the synchronous bridge call held the session mutex. ADR 0025
moves the engine to a worker; a live click at 15 s now leaves 92.3% coverage and
2251 ms p95 (no click: 92.3% / 2263 ms). Evidence:
`docs/qa/2026-11-25-asr-chunk-confirmation.md`.

## What would overturn it

- UIA changes lag actual paint by more than one frame or miss short-lived
  captions; then add a native frame/present hook.
- A candidate improves latency but fails a longer multilingual WER/CER run or
  increases fragmentation enough to harm simplification.
- GPU inference becomes the shipping path; then fork the same harness into
  explicit CPU and GPU provider tracks with separate model/runtime records.
