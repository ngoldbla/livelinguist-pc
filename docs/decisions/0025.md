# 0025 - Run click simplification outside the bridge lock

- Status: accepted
- Date: 2026-11-25
- Decision IDs: D-062
- Related: 0012 (event envelope), 0021 (packaging), 0024 (caption-latency
  benchmark and 560 ms default); plan `docs/plans/2026-11-24-autoresearch-plan.md`
  Stage C.
- Evidence: `docs/qa/2026-11-25-asr-chunk-confirmation.md`

## Context

`onSimplify` called the synchronous napi `simplify` while the bridge held the
session mutex and the pipeline's simplifier engine. The UI thread waited on the
napi call and the capture thread waited on the mutex, so a click stopped live
captions until the backend returned. On long captions that was tens of seconds;
the click gate measured the last caption observation at the click for the rest
of the run. The installed rc.1 reproduced it, so rc.2 shipped with it.

The LLM itself is not slow: `ll-eval --scenario click-bench` measures 1.28 s p50
and 1.33 s p95 over three clicks on the reference PC. The defect is ownership:
the backend ran inside the lock that audio feeding and the UI share.

## Options

1. **Borrow the engine to a worker (chosen).** `simplify` claims the click in the
   queue, takes the `SimplificationEngine` out of the pipeline, sets a
   per-session ownership token, and returns a `queued` acknowledgement. A
   worker thread runs the engine outside the bridge lock, re-locks only to store
   and emit the result, then returns the engine. The UI keeps its spinner until
   the `simplified` event and no longer waits on the backend.
2. Make only the napi call asynchronous. The UI would paint, but the capture
   thread would still block on the session mutex and audio would overrun.
3. Cap generation time and tokens. A mitigation, not a fix; a long caption still
   freezes the pipeline and the UI for seconds.
4. Move the whole pipeline behind a finer-grained lock. More churn and more
   concurrency surface for the same result.

## Decision

Option 1. The engine is single-flight (the click queue already has one active
and one queued slot). The ownership token is per session so a worker from a
previous session cannot clear or overwrite a new session's engine. Cancellation
after the backend returns discards the result and advances the queue, as before.
The `simplified` event remains the only path that updates the store for a queued
click; the synchronous return is only an acknowledgement.

## Consequences

- Audio keeps feeding while the LLM runs; partial events continue and the UI
  stays responsive.
- A click can no longer be observed by waiting on the napi return. Callers read
  the `simplified` event (the UI already does) or the snapshot.
- The bridge reports `status: "queued"` for accepted work. Cached results still
  return immediately with their text.
- The pipeline's `engine` is now optional while a worker owns it. The dev-only
  automatic path stores the segment unsimplified if it cannot borrow the engine;
  it never blocks audio.
- Tests: `worker_job_path_keeps_the_pipeline_usable` feeds audio while the
  engine is out and then applies the result. The live click gate feeds audio
  through a real session: 92.3% coverage and 2251 ms p95 with a click at 15 s
  (no click: 92.3% / 2263 ms).

## What would overturn it

- A worker that fails to return the engine (panic, poisoned mutex, session
  stop) leaves the session without simplification. The token and the
  per-session check make that visible; a restart is the recovery.
- If click-to-simplified latency regresses materially, the worker handoff or the
  backend warm-up is the place to look, not the event path.
