# 0003 — System audio capture

- Status: accepted
- Date: 2026-11-21
- Decision IDs: D-007 + §13
- Master plan: `docs/plans/2026-11-21-live-linguist-pc-master-plan.md`

## Context

Captions must hear the call/video app, not only the microphone. Windows is the product; Linux is dev/eval.

## Options

WASAPI loopback captures the system mix without a virtual driver on Windows. On Linux, PipeWire monitor sources are available through cpal/Pulse/pipewire; a virtual sink is a stable optional route. Native Wayland varies by compositor.

## Decision

Windows: WASAPI loopback is the primary system-audio path (S-5W chooses between cpal and the `windows`/WASAPI crate). Linux dev: PipeWire monitor source is the default; `pw-loopback` virtual sink is optional. File, demo, and silence sources are always available for eval.

## Consequences

Easy: no driver install on Windows. Hard: Windows loopback is per-output-device; Linux monitor names vary. Revisit if WASAPI loopback fails on a real call (S-5W gate).

## Evidence

`core/crates/ll-audio`; `docs/qa/2026-11-21-audio.md`; S-5W is pending Windows hardware.

## Addendum 2026-11-23 — Windows capture stack

cpal 0.18 WASAPI loopback on the default render endpoint (input stream on the
output device). Evidence: docs/qa/2026-11-23-audio-loopback.md.

## Addendum 2026-11-25 — microphone and endpoint selection

The same cpal path now captures microphone endpoints, and either direction can
open a specific WASAPI endpoint by stable id (ADR 0028). Loopback still uses an
input stream on a render device; a microphone uses an input stream on a capture
device. An explicit endpoint is pinned; only an unspecified selection follows
the Windows default. Evidence:
`docs/qa/2026-11-25-microphone-device-selection.md`.
