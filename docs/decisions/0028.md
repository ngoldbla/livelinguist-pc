# 0028 - Microphone capture and selectable Windows audio endpoints

- Status: accepted
- Date: 2026-11-25
- Decision IDs: D-065
- Related: 0003 (system-audio capture), 0018 (v1.0 scope), 0026 (console flow)
- Evidence: `docs/qa/2026-11-25-microphone-device-selection.md`

## Context

`v1.0.0-rc.4` captures Windows' **default render endpoint** through WASAPI
loopback and lists the microphone as `available: false, note: "post-1.0"`.
Two user-facing gaps follow:

- A machine with several render endpoints (HDMI, S/PDIF, USB headset, virtual
  cable) captures whichever one Windows currently marks default. If the call or
  video plays on another endpoint, the app hears silence and looks broken.
- A headset microphone is the natural source for in-person speech, and the
  capture code already has the ring buffer, downmix and resampling path that a
  microphone needs.

The master plan expected microphone capture eventually; the v1.0 freeze deferred
it. Users now ask for both the microphone and a way to pick the endpoint.

## Options

1. **Keep the default render endpoint only.** Smallest change; still fails on
   multi-endpoint machines and leaves microphone users out.
2. **Add the microphone but keep the endpoint hidden.** Doubles the source types
   without solving the "wrong output" failure.
3. **Add microphone capture and an endpoint picker (chosen).** Enumerate cpal/
   WASAPI endpoints for both directions, pass a stable endpoint id into session
   start, persist the choice per direction, and never silently replace an
   explicit selection.

## Decision

Option 3.

- `ll-audio::capture` exposes `CaptureKind::{Loopback, Microphone}`,
  `list_devices(kind)`, `default_device_id(kind)`, and one `DeviceCapture` that
  opens the selected endpoint (or the default) and shares the existing ring,
  downmix and `rubato` resampling path.
- `DeviceCapture` accepts f32 plus the common integer and f64 endpoint formats,
  converting to f32 in the callback, instead of rejecting a non-f32 device.
- `start` takes an optional `deviceId`. A missing or malformed id is an explicit
  `AUDIO_SOURCE_UNAVAILABLE` error; it never falls back to another endpoint.
  Only an unspecified selection follows Windows' default changes.
- The bridge exposes `devices` and `defaultDeviceId` on the `monitor` and `mic`
  entries from `listAudioSources`; `source` becomes `mic` for microphone capture,
  and real ASR/simplification run for it exactly as for system audio.
- The console keeps the two decision tiles and adds a **Device** selector under
  them when system audio or microphone is selected. The list refreshes when the
  SOUND menu opens. The chosen endpoint id is saved as `outputDeviceId` or
  `inputDeviceId`; an empty value means "follow Windows' default".
- At start, a saved id that is no longer present is dropped to the default with
  a visible toast, rather than failing the session on stale hardware.
- Microphone audio stays in the existing local pipeline; nothing is recorded or
  transmitted. Windows microphone permission is required.

## Consequences

Easy: the app hears the call on the endpoint the user chooses, and a headset
microphone works. Endpoint names make the SOUND choice concrete, and the default
entry names Windows' current default.

Hard: the v1.0 scope grows by one source and one picker; the Windows microphone
privacy prompt and device permission become support surfaces. Endpoint ids are
stable across runs but can change after driver reinstalls, so the UI must handle
a stale id. An explicit endpoint that disappears mid-session is retried by id
and then stops the session honestly; it is not swapped for the default.

## What would overturn it

- Windows per-app loopback becomes available and reliable: offer app capture as
  a third source, keeping endpoint selection for system audio.
- Users need automatic endpoint following while an explicit device is chosen:
  revisit the "explicit is pinned" rule only with a visible indicator.
- cpal's WASAPI endpoint ids prove unstable across normal reboots: store the
  endpoint name as a secondary key and re-resolve it, without fuzzy matching
  that could capture a different device silently.
