# 0017 — Measure the renderer and accelerators; never declare them

- Status: accepted
- Date: 2026-11-22
- Decision IDs: D-054 (corrected from the earlier D-052, which the master plan
  uses for Linux packaging)
- Master plan: `docs/plans/2026-11-21-live-linguist-pc-master-plan.md`

## Context

`RuntimeStatus.uiBackend` was declared from `cfg!(target_os)`: every Windows
build said `d3d12` even on a machine with only the Microsoft Basic Display
Adapter. `probeBackends()` guessed CUDA from `LL_CUDA_AVAILABLE` and Vulkan from
a Linux-only ICD path, so a real Windows GPU could never appear and a
GPU-less machine could still look accelerated. That conflicts with golden rule 6
(never claim a no-GPU GUI works).

## Options

1. Keep the target-OS declaration and add a manual override flag.
2. Ask GPUIX for its renderer identity (no such API in 0.11).
3. Probe the platform: DXGI adapter enumeration on Windows, DRM render nodes and
   Vulkan ICDs on Linux, the CUDA driver API for accelerator devices; report
   `unknown` until probed.

## Decision

Option 3. `ll-accel` is the single probe. `RuntimeStatus.ui` carries the measured
backend, API availability, hardware flag, adapter, and a degraded reason.
`probe_hardware` returns the full adapter/runtime report; `probe_backends` maps
it to backend availability. A software-only adapter is reported as degraded and
the UI surfaces the reason; strict GPU scenarios still fail loudly. The CUDA
probe calls `cuInit`/`cuDeviceGetCount`/`cuDeviceGetName`/`cuDeviceTotalMem`;
`nvcuda.dll` being loadable is not treated as a device.

## Consequences

Easy: one honest source for the dev panel, the backend probe, and future
calibration keys. Hard: adapter names come from the driver and can change; a
missing ICD makes Vulkan unavailable even when the loader exists. GPUIX's own
per-frame adapter choice is still not observable, so evidence claims the
enumerated adapter and the working DirectX code path, not each presented frame.
