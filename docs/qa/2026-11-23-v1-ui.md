## Keyboard

Implemented (T27):

- Caption rows (`CaptionRow` in `ui/src/aurora/components.tsx`) are
  `role="button"`, `tabIndex=0`, with the focus ring (`focusVisible`).
  Tab reaches the list; **Up/Down** (also Home/End) move between sentences;
  **Enter/Space** runs the same simplify call as a click.
- Accessible label = sentence text + state: `Click to simplify`, `Simplifying`,
  or `Simplified: <text>` (UI only, never logged).
- **Read latest** button label shows `Ctrl+Shift+L`; the shortcut works
  window-wide (GPUIX window `onKeyDown` → `windowKeys` bus in
  `ui/src/captionKeys.ts`).
- **Announce method:** GPUIX 0.11 has no live-region/announce API, so Read
  latest moves keyboard focus to the latest caption row (newest simplified,
  else newest). The screen reader reads the row's label.
- GPUIX has no imperative `focus()`. Moving focus remounts the target row with
  `autoFocus`. Focus moves only after the user's own key press.

Evidence: `bun test src/captionKeys.test.ts` — 9 tests on the pure handler
(index + key → index/action, shortcut, label, latest-row choice, key bus).

Pending (Windows): a keyboard-only run (no mouse) that starts a session, moves
to a caption, simplifies it, and uses Read latest; `verify-windows.ps1 -A11y`
still passing; focus ring visible at 100/125/150%.

## Reduced effects

The **Reduced effects** setting turns off the live Aurora glow
(`AuroraField active={screen === "live" && !settings.reducedEffects}`). The UI
has no animations (no `motion` or timers in `ui/src`), and GPUI redraws only
when state changes, so there is no frame loop to cap. The old setting text
promised a "30 fps target". It now says what the setting does.

## Work area (T23)

`workArea()` returns JSON `{ x, y, width, height, scale }` and works before any
session exists; the UI reads it before opening a window (`readWorkArea` in
`ui/src/bridge/transport.ts`, then `sizeForMode`).

Run 2026-11-24 on the reference PC: one 2560x1080 display, 48 px taskbar,
`node -e "const c=require('./ui/livelinguist-core.node'); console.log(new c.CoreClient().workArea())"`.

| Display scale | `workArea()` (node, DPI-unaware) | Same monitor, physical |
|---|---|---|
| 100% | `{"x":0,"y":0,"width":2560,"height":1032,"scale":1.0}` | work area 2560x1032 (dpi 96) |
| 150% | `{"x":0,"y":0,"width":1707,"height":672,"scale":1.0}` | work area 2560x1008 (dpi 144) |

Why `scale` is 1.0 in both rows: Node is DPI-unaware, and Windows virtualizes
both the rectangle and the DPI for an unaware process, so the call returns the
**logical** size. `width / scale` is the logical size in either awareness mode,
which is what the layout uses — that is the documented contract in
`ll-window/src/win32.rs`.

The app is per-monitor aware and gets the physical numbers: at 150% it sized the
Console to a 1770x972 physical client area (1180x648 logical) inside the
2560x1008 physical work area, and the whole screen still fits (screenshot
`docs/screenshots/m2-windows/overlay/console-150.png` is from the W-1 matrix).

Observed, cosmetic, left to T25: the window keeps its centred position, so at
150% the client bottom lands 13 px below `rcWork` (client top 49). No control is
hidden — the Console's own bottom padding absorbs it and **Start captions** is
fully visible — but positioning the window inside the work area rather than only
sizing it is a T25 layout item.
